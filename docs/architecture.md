# Архитектура маркетплейса

## Overview

Маркетплейс позволяет продавцам размещать товары, а покупателям — получать персональную ленту, оформлять и оплачивать заказы. После изменения статуса заказа покупатель получает уведомление.

Целевая архитектура состоит из шести доменных сервисов, API Gateway, Kafka и отдельных баз данных. Она показана на [C4 Container диаграмме](diagrams/container.puml). Для просмотра используется PlantUML со стандартной библиотекой C4.

В репозитории реализован только каркас Catalog Service на Python 3.12 и FastAPI с `GET /health`. Все бизнес-функции, остальные сервисы, Kafka и базы данных описаны только на уровне архитектуры и не запускаются в Docker Compose.

## Domains

| Домен | Ответственность | Сервис | Данные домена |
| --- | --- | --- | --- |
| User | Управление покупателями, продавцами и их профилями | User Service | Пользователи, роли, профили и контакты |
| Catalog | Управление товарами и их принадлежностью продавцу | Catalog Service | Карточки, категории, цены, идентификаторы продавцов |
| Feed | Персональная выдача и ранжирование товаров | Feed Service | История просмотров, предпочтения по категориям, показатели популярности |
| Order | Оформление заказа и управление его состоянием | Order Service | Заказы, позиции, снимки цен, итоговые суммы, статусы |
| Payment | Создание и учет платежей | Payment Service | Платежи, суммы, валюта, статусы, идентификаторы провайдера |
| Notification | Уведомление покупателя о статусе заказа | Notification Service | Уведомления, получатели, попытки и результаты отправки |

## Services and responsibilities

Каждый бизнес-домен выделен в отдельный сервис. User Service отвечает за профиль, Catalog Service — за исходные данные товара, Feed Service — за порядок показа товаров. Такое разделение позволяет менять правила ленты без изменения управления каталогом.

Order Service хранит состав заказа, фиксирует стоимость позиций на момент оформления и управляет статусом заказа. Payment Service принимает сумму и валюту заказа, создает платеж у провайдера и учитывает его результат. Успешное создание платежа еще не означает успешную оплату. Notification Service отвечает за отправку уведомления, поэтому ошибка отправки не должна отменять изменение заказа.

API Gateway направляет запросы клиентов в нужные сервисы и не содержит бизнес-данных. Kafka передает события между сервисами. Это технические контейнеры, отдельные бизнес-домены за ними не закреплены.

## Data ownership

| Сервис | Собственная БД | Что хранит |
| --- | --- | --- |
| User Service | User DB | Пользователи, роли, профили и контакты |
| Catalog Service | Catalog DB | Карточки, категории, текущие цены, связь товара с продавцом |
| Feed Service | Feed DB | Просмотры, предпочтения, популярность, копия данных товара для ранжирования |
| Order Service | Order DB | Покупатель, состав заказа, снимки цен, сумма, история статусов и контакт для уведомления по заказу |
| Payment Service | Payment DB | Связь платежа с заказом, сумма, валюта, статус и идентификатор у провайдера |
| Notification Service | Notification DB | Событие-основание, получатель, содержание и результат отправки |

Для каждой БД предполагается PostgreSQL. Доступ к ней имеет только сервис-владелец. Общих баз и прямого чтения чужих таблиц нет: данные передаются через API или события.

Идентификатор продавца в Catalog DB не делает Catalog Service владельцем профиля продавца. Копия товара в Feed DB нужна для ранжирования; источником актуальной цены остается Catalog Service. Цена в заказе — исторический снимок и не меняется при последующем редактировании карточки. Контакт в заказе сохраняется при оформлении и передается Notification Service в событии, поэтому ему не нужен доступ к User DB.

## Synchronous interactions

| Кто обращается | К кому | Протокол | Назначение |
| --- | --- | --- | --- |
| Buyer | API Gateway | HTTPS | Лента, карточки, профиль и заказы |
| Seller | API Gateway | HTTPS | Профиль продавца и управление товарами |
| API Gateway | User Service | HTTP/REST | Работа с пользователями и профилями |
| API Gateway | Catalog Service | HTTP/REST | Просмотр каталога и управление им |
| API Gateway | Feed Service | HTTP/REST | Получение ленты и передача просмотров |
| API Gateway | Order Service | HTTP/REST | Создание и просмотр заказов |
| Order Service | Payment Service | HTTP/REST | Создание платежа с идентификатором заказа, суммой и валютой |
| Payment Service | Payment Provider | HTTPS | Создание платежа и проверка результата оплаты |
| Feed Service | Catalog Service | HTTP/REST | Получение актуальных данных выбранных товаров перед выдачей |

В этих связях вызывающая сторона ожидает ответ. Обращение каждого сервиса к собственной БД выполняется по протоколу PostgreSQL с SQL-запросами; на диаграмме оно обозначено отдельно от HTTP.

## Asynchronous interactions

| Событие | Публикует | Получает через Kafka | Результат |
| --- | --- | --- | --- |
| `PaymentSucceeded` | Payment Service | Order Service | Заказ отмечается как оплаченный после подтверждения провайдера |
| `OrderStatusChanged` | Order Service | Notification Service | Отправляется уведомление о новом статусе заказа |
| `ProductUpdated` | Catalog Service | Feed Service | Обновляются локальные данные товара для ранжирования |

Событие оплаты содержит идентификаторы платежа и заказа, сумму и валюту. Событие статуса содержит заказ, новый статус и контакт получателя. Событие товара содержит его идентификатор, категорию, дату публикации и версию изменения.

Изменения доходят до подписчиков с задержкой. События могут приходить повторно, поэтому обработчики должны проверять идентификатор события и не повторять уже выполненное действие. Это требование к будущей реализации, обработчиков в проекте пока нет.

## Personalization approach

Feed Service получает просмотры от клиента через API Gateway и хранит их в Feed DB. По истории просмотров определяются предпочтения пользователя по категориям. Популярность товара оценивается по числу просмотров за последнее время, свежесть — по времени, прошедшему с публикации товара.

Для ранжирования используется взвешенный score: интерес к категории, популярность и свежесть приводятся к общей шкале и складываются с выбранными весами. Товары с большим score показываются выше. Для нового пользователя без истории учитываются популярность и свежесть.

Событие `ProductUpdated` обновляет данные для ранжирования. Перед выдачей Feed Service запрашивает актуальные карточки у Catalog Service. Алгоритм описан как концепция и не реализован в коде.
